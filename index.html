Problem

Recruiters know what they want in plain language — “I need a TikTok/Instagram video editor” — but a job listing that candidates can actually apply to needs far more: required skills, responsibilities, target platforms, location, salary, and screening questions. Writing that out is slow, and asking a model to do it in one shot produces confident, invented requirements.

Solution

A conversational job-posting layer for Arclent, the online recruiting platform I'm building. The recruiter describes the role however they like; a LangGraph workflow works out what's missing, collects it through structured choices, and produces a complete, application-ready job description that the recruiter can edit and publish. It runs live as a standalone tool and slots into the wider platform as its job-posting layer.

How it works

Natural-language request→ AI information collection→ Structured job description→ Recruiter editing→ Published job→ Candidate application

The conversation is a multi-step state machine, not a chat loop. Each turn knows which fields are still unfilled, asks about one of them, and writes the answer back into a structured job state that the live preview panel reads from.

Engineering problems solved

  • Hallucinated requirements. Generation is constrained so the model can't invent degrees, certifications, years of experience, salary figures or tools that were never mentioned. Fields with no supporting input are surfaced as questions rather than quietly filled in — the recruiter stays in control of every requirement that reaches a candidate.
  • Edits being overwritten. Recruiter edits become the source of truth. Regeneration proofreads and enhances the existing content instead of replacing it, so a hand-written responsibility survives the next AI pass.
  • State drift. The job description is held as structured state rather than free text. The chat, the live editing panel and the published listing all read from and write to that one state, so they can't diverge.

Key features

  • Guided collection of skills, responsibilities, target platforms, location, salary and other requirements
  • Recruiter-authored screening questions attached to the listing
  • Creator-platform targeting with badges — YouTube, TikTok, Instagram, Twitch
  • Multi-tenant recruiter dashboard with hiring-status controls
  • Admin view across posted roles, plus a public job board and candidate application flow
  • Chat-first responsive UI with a live job-info panel beside the conversation

Goal

Build one workspace where an agent can genuinely act — search documents, query a database, read and send email, run research — without that power turning into a liability. Most of the work is in the boundaries: what the model is allowed to do, what it has to ask permission for, and what it never gets to touch directly.

Architecture

Mistral APITavilyGmail API SQLiteChroma

Three independent processes over defined interfaces. The LLM's tool calls never receive a trusted user identity as an argument — identity is resolved server-side.

The Streamlit client never touches the database, the LLM provider or the tools directly. Every request goes through the FastAPI backend, which is the single place where authentication, authorisation and tool permissions are decided.

The core agent

A LangGraph StateGraph with chat_node, tool_router, human_approval and cancel_node. Destructive tools are routed through interrupt(), which pauses the graph until a human approves or cancels. Graph state is checkpointed with AsyncSqliteSaver, so multi-turn memory and pending approvals survive a server restart rather than dying with the process.

Seven modules

Chat / core agentTool-calling state machine with routing, approval gating, cancellation and durable checkpointing.
Resume evaluatorPDF upload, structured extraction, Pydantic schema validation, conversational editing, JD keyword-overlap scoring and LLM qualitative analysis. Tailored generation may only reorder and reword existing content — it cannot fabricate skills or experience.
Tables — natural language to SQLCreate and query tables in plain English, behind identifier allowlists, user namespacing, parameterised inserts, SELECT-only restrictions, blocked-keyword validation, current-table enforcement, LIMIT caps and read-only SQLite execution.
CRAG — corrective RAGRetrieve → grade → generate. A dedicated grader LLM labels each retrieved chunk correct, ambiguous or incorrect, and triggers live Tavily search when retrieval is too weak to answer from.
ResearchMindSearch → reader → writer → critic → one bounded revision. Tavily handles search and extraction; the system builds structured notes, writes a cited report, critiques the draft, revises once when needed, and streams progress to the client.
Email agentGmail API with OAuth2 and PKCE, LangGraph drafting with self-critique and revision, Chroma semantic inbox search. Sending and saving drafts are dangerous actions and require approval.
Job trackerLLM extraction of company, role and event type; company-name normalisation; fuzzy matching with difflib using role as a disambiguator; status derived from the event timeline; idempotent, resumable synchronisation.

Important engineering decisions

  • No embeddings for entity identity. The job tracker deliberately avoids vector similarity for deciding whether two emails belong to the same application. Semantic closeness is not identity — “Senior Engineer at Acme” and “Engineer at Acme Corp” can be near-identical vectors and different applications, or distant vectors and the same one. Normalisation plus fuzzy matching plus role disambiguation is the right tool for that job.
  • Safety at the database boundary, not in the prompt. The NL-to-SQL module assumes the model will eventually be talked into writing something destructive, so the connection itself is read-only and the identifiers are allowlisted. Prompt instructions are a preference; a read-only connection is a guarantee.
  • Approval as graph state. Because approvals are checkpointed rather than held in memory, a pending “send this email?” survives a restart instead of silently disappearing.

Goal

Forecast multiple coupled climate variables twelve months ahead across a spatial grid, where every cell's future depends on both its own history and on what its neighbours are doing.

AI/ML approach

Three stages. A graph convolutional encoder learns spatial structure across grid nodes; a GRU aggregates the temporal window into a latent state; a continuous-time neural ODE evolves that state forward and the forecast is read out from the integrated trajectory.

Climate grid→ Spatial graph (8-connectivity)→ 3-layer GCN encoder→ GRU aggregator→ Neural ODE (RK4)→ 12-month forecast

Why a graph

Climate grid cells are not independent samples. Modelling the domain as a graph with 8-connectivity lets spatial dependence be learned rather than assumed away, and keeps the same model applicable to irregular domains.

Why a neural ODE

Monthly observations are discrete samples of a continuous process. A neural ODE parameterises the derivative of the latent state and integrates it forward, so the forecast horizon becomes an integration bound rather than a fixed number of unrolled steps.

Technical implementation

  • Three-layer GCN encoder with LayerNorm and residual connections → GRU temporal aggregator → continuous-time neural ODE solved with RK4 via torchdiffeq; roughly 700K parameters
  • CRU TS reanalysis data: 122 years of monthly observations (1901–2022), 8 coupled climate variables
  • 2,400-node graph over a 40×60 grid with 8-connectivity
  • 24 months of input history mapped to a 12-month-ahead forecast
  • Custom asymmetric loss for precipitation skew: log1p transform plus a weighted under-prediction penalty

Results

R² 0.83 and RMSE 14.20 on the 2,400-node configuration, evaluated against a GCN-GRU ablation baseline that isolates how much of the performance comes from the neural ODE rather than the graph encoder alone. Per-variable accuracy is highest on temperature and lowest on precipitation — the expected pattern given precipitation's skew and variance.

Problem

Onboarding a company onto a recruiting platform means typing out details that already exist on the company's own website. Handing that to a model naively produces two failures at once: a confidently invented company profile, and a backend that will fetch any URL a user hands it.

Solution

A recruiter enters a company website URL. The backend researches that site — and public sources where necessary — extracts and normalises the information with Mistral through a LangGraph pipeline, and returns a structured, editable company profile for the recruiter to confirm before anything is stored.

Pipeline

Company URL→ Safe URL validation→ Website crawling→ Page discovery→ HTML / metadata extraction→ Public-source enrichment→ Mistral structured extraction→ Evidence consolidation→ Confidence assessment→ Editable profile→ Human confirmation → persistence

Engineering problems solved

  • Grounding. Extracted fields are tied back to the evidence that produced them and carry a confidence assessment, so a recruiter can see what was actually found versus what was thin — rather than receiving a uniform-looking profile where half the fields were guessed.
  • SSRF. A backend that fetches user-supplied URLs is an SSRF vector by default. This one validates URLs and redirect targets, blocks unsafe destinations, and caps requests, response sizes, crawl depth and total pages.
  • Streaming. Crawling takes time, so progress is streamed to the client with NDJSON instead of leaving the recruiter on a spinner.

Problem

Detailed Project Reports have to be checked against guidelines, and the check has to be defensible — a reviewer needs to know which page a finding came from and which rule it violated. A summary from a language model is neither auditable nor reliable enough for that.

Solution

A working MVP that ingests DPR PDFs, extracts and cleans the text with OCR fallback for scanned pages, and evaluates the content against a local guideline knowledge base — producing an explainable, page-referenced compliance and risk report.

The important distinction

This is deliberately not PDF → LLM → summary. It is a hybrid pipeline where deterministic rule checks and retrieval do most of the work, and the LLM is invoked only where genuine reasoning is required. Risk scoring is deterministic, so the same document produces the same score twice.

DPR PDF→ Extraction + OCR fallback→ Guideline KB retrieval (RAG)→ Deterministic rule checks→ LLM reasoning where needed→ Schema validation→ Page-referenced report

Key features

  • PDF ingestion with text extraction, cleaning and OCR fallback for scanned pages
  • Retrieval against a local guideline knowledge base
  • Deterministic rule checks alongside LLM reasoning
  • Schema validation on structured outputs
  • Explainable findings with page references and deterministic risk scoring
  • LangGraph orchestration across the whole pipeline

Goal

Forecast climate variables twelve months ahead across a 126-node Kashmir domain, and answer a question the architecture alone can't: does the way you build the graph actually matter?

Approach

A GCN-ODE (GraphNODE) model — a graph convolutional encoder feeding a continuous-time neural ODE — trained across an ablation grid that varies both the domain and the edge construction.

The ablation

  • Domain: a wide South Asia grid against the Kashmir-only 126-node domain, including slicing the wide-domain weights down to the Kashmir nodes to separate transfer from retraining.
  • Graph construction: geographic edges only, against a hybrid graph adding top-k correlation-based teleconnection edges — testing whether statistically linked but geographically distant nodes carry signal that adjacency misses.
  • Training variants: hidden size, epoch count, per-node normalisation, distance-weighted edges, DropEdge, finer ODE integration and learning-rate warmup.

What the comparison is for

Precipitation is the hardest variable in the set — skewed, high-variance, and the one a forecast is most often wanted for. Running geographic and hybrid variants under matched training settings is what makes any difference between them attributable to the graph rather than to the optimiser.

Context

B.Tech capstone at the University of Kashmir, supervised by Er. Khalid Hussain, with two teammates.

Goal

Give an LLM access to tools that live in different places, without hard-wiring each integration into the application.

Solution

A multi-server architecture that connects LLMs to external tools and services through the Model Context Protocol. Tool servers stay independent processes with their own concerns; the client discovers what each one offers and routes calls to the right server.

Why it matters

MCP turns an integration problem into a protocol problem. Adding a capability means standing up a server that speaks MCP, not editing the agent — which is the difference between a demo and something you can keep extending.

Problem
